# 18. Recommended Target Architecture: YouTube Music Video Party Platform

This document presents the target software architecture for transforming Jukebox into a synchronized YouTube Music Video Party platform while adhering to technical, legal, and platform constraints.

---

## 1. The YouTube Music Audio/Video Architecture

### Understanding the YouTube Music Media Model
Research into YouTube Music's internal media architecture reveals how Google implements the Song / Video toggle:

1. **Two Distinct Entities**: In the YouTube catalog, an official audio track ("Art Track") and its official music video are stored as **two distinct video assets**, each with its own unique 11-character `videoId`.
   - **Audio / Song Version**: Typically generated by music aggregators (Universal, Sony, Warner) with static album art and high-fidelity audio stream.
   - **Video Version**: The official high-definition music video uploaded to the artist's Official Artist Channel (OAC).
2. **The Counterpart Association**:
   YouTube Music's backend links these two assets together via the **`counterpart`** identifier in its player and playlist payloads (`musicPlaybackSwitcherRenderer`).
3. **The Switcher Mechanism**:
   When a user clicks "Song" or "Video" in the native YouTube Music app, the client swaps the active `videoId` to its counterpart while maintaining the exact playback timestamp ($\Delta t = 0$).

## 2. YouTube Music Integration Strategy (Legal & Supported)

Per project requirements:
- **No Unofficial Extraction / Stream Ripping**: Do not rip audio streams or proxy copyrighted Google media through custom servers.
- **Official Embedded Playback**: Deliver playback through the **YouTube IFrame Player API** embedded directly in the client.
- **Counterpart Resolution Engine**:
  1. **Primary**: YouTube Music API search and watch playlist metadata extraction via internal Innertube `counterpart` mapping.
  2. **Secondary**: YouTube Data API v3 music category query (`videoCategoryId=10`) with Official Artist Channel title matching.
  3. **Data Contract**: Every song in the Jukebox queue holds:
     ```typescript
     interface QueueItem {
       id: string;
       roomId: string;
       audioVideoId: string;    // Song / Art track ID
       musicVideoId: string | null; // Official Music Video counterpart ID
       hasVideo: boolean;       // True if counterpart music video exists
       title: string;
       artist: string;
       duration: number;
       thumbnail: string;
     }
     ```

## 3. Responsive Dual-Mode Player Architecture

Instead of an invisible 1px offscreen element, the `Player` component in `packages/client/src/components/room/Player.tsx` will support two visual modes:

1. **Audio Mode (Default)**:
   - Renders the classic retro Jukebox arch frame with spinning neon record, vibrant album art, and audio visualizer effects.
   - The YouTube IFrame operates silently in the background container, delivering uninterrupted audio playback.
2. **Video Mode (Synchronized)**:
   - The player container expands into a responsive 16:9 cinema viewport within the neon frame.
   - The YouTube IFrame switches to the `musicVideoId` counterpart at the exact current timestamp.
   - Participants watch the official music video with video controls synchronized across the room.
3. **Graceful Fallback**:
   - If a participant encounters an embedding restriction (`event.data === 101 || event.data === 150`) or regional block, the client detects the error, displays an informative non-blocking notice ("Official video is restricted from embedding in your region; falling back to synchronized audio"), and continues playing audio seamlessly.

## 4. Frictionless Guest Access & Instant QR Code System

1. **Guest Authentication Flow**:
   - When an unauthenticated user submits the join form on `/` or `/join/[code]`, the backend generates a signed Guest JWT (`role: 'guest'`, `guestId: uuid`).
   - The client stores this token in `sessionStorage` and connects to Socket.IO.
   - Database foreign keys in `room_members` are updated to support guest identifiers without requiring an entry in `users`.
2. **Automatic QR Code Generation**:
   - Each room automatically generates a high-contrast SVG/Canvas QR code using `qrcode.react`.
   - The QR code encodes `${APP_URL}/join/${roomCode}`.
   - Available via an "Invite & QR Code" modal accessible to all members with one-click PNG download and clipboard copy.

## 5. Server-Authoritative Synchronization Engine

1. **Host-Enforced Permissions**:
   - Backend socket handlers verify `socket.data.userId === room.host_id` for all mutative events (`play`, `pause`, `seek`, `next_track`, `toggle_video_mode`).
   - Non-host participants can only emit `add_song` (subject to cooldowns) and `request_sync`.
2. **Two-Way Clock Synchronization**:
   - Client sends `request_sync` with `clientSendTime = Date.now()`.
   - Server responds with `{ serverTimestamp, playbackState, position, isVideoMode, currentTrack, clientSendTime }`.
   - Client calculates RTT:
     $$\text{RTT} = \text{Date.now()} - \text{clientSendTime}$$
     $$\text{CorrectedPosition} = \text{position} + \frac{\text{RTT}}{2000}$$
   - Late joiners and reconnected participants seamlessly converge to the exact track, position, and video mode.
